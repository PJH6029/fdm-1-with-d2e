My recommended exit rule:

Exit Phase 0 if pinned official evaluate.py scores ground_truth.mcap vs your_roundtrip_prediction.mcap at the expected near-perfect values on at least one real recording, and the artifact proves the prediction file was generated by your writer rather than copied from ground truth.

For that check, use the same Apex recording you already used. Require approximately:

num_bins: same as prior official run, or explained by intentional truncation
mouse pearson_x/y: ~1.0
scale_ratio_x/y: 1.0
mouse_button button_accuracy: 1.0
keyboard key_accuracy: 1.0

Also record something like file hash/size/provenance so the prediction MCAP is clearly not the same file copied as prediction.

I would add one negative control as a bonus, but not as a separate blocker: shift predicted keyboard/mouse events by one 50ms bin, or zero the mouse deltas, and confirm at least one official metric degrades. This catches a surprisingly common confound: a round-trip test that looks perfect because the evaluator is comparing aligned empty regions, ignoring missing event classes, or accidentally reading the same file twice.

The main hidden assumptions I see are:

Same-MCAP official evaluation is being interpreted as writer validation. It validates the official evaluator runtime and the source MCAP, but not necessarily your writer output.

Local perfect metrics may be tautological. If your local reader, binning, tokenizer, de-tokenizer, writer, and local evaluator share assumptions, all-1.0 local scores are necessary but not independent evidence. The official evaluator is the independent oracle.

One-game official evaluation may miss schema/topic edge cases. Apex likely exercises mouse movement and common keyboard input, but some games may expose different keyboard sparsity, button usage, duration/tail behavior, or screen timestamp quirks. This is not a Phase 0 blocker if the per-game JSON distribution pass already exercised one recording per game, but it should become an early Phase 0.5 smoke.

--from-mcap-json may not be the final reader path. If JSON extraction and native OWAMcap reading differ, the distribution run may validate the JSON bridge more than the production reader. A cheap Phase 0.5 check is binary-reader vs JSON-reader agreement on event counts, first/last timestamps, bin counts, and aggregate mouse/key/button totals for a few recordings.

The 459-pair manifest is internally credible but not externally proven complete. Public D2E describes 267 hours and 29 games, but the exact recording count may vary by released subset/version; your manifest should be treated as the reproducible corpus snapshot, ideally with path, size, and maybe hashes.
